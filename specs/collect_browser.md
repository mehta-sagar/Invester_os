# Spec collect_browser   (from brief S1-T7, task S1-SPEC4, 28 Nov 2026)

The real-Chrome transport that lets the RSS poller read NSE's archive host again, plus the host-down rule that stops one dead host from eating the poll cycle. Trigger (R3b of `specs/collect_rss.md`, Sagar, 28 Nov): `nsearchives.nseindia.com` refuses every non-browser client whatever the User-Agent (curl HTTP/2 rejected in about 0.06 s; curl HTTP/1.1 and Python urllib hang to timeout), while the Mac's own browser gets the same XML in 39 ms (200). The 23 NSE rows therefore ship `enabled=no`. Decision basis: `docs/decisions/0002a-real-browser-backfill.md` (access mode `real_browser`; no stealth), which Sagar re-confirmed for this use on 28 Nov ("the next task, a real-Chrome transport, never by faking a browser from a script").

Modules: `src/investos/acquire/browser.py` (new: `RealBrowserTransport`, driver layer, reaper, header sanitiser), `src/investos/acquire/rss.py` (amended: routing, `RssNseFeedCollector`, host-down rule, notification coalescing, source-aware state/manifest reads), `src/investos/check/rss_check.py` and `src/investos/parse/rss_items.py` callers (amended to read two sources), `src/investos/cli.py` (`collect rss` wires the transport), `pyproject.toml` (optional extra `browser`), `config/investos.example.toml` (commented block only), `ops/launchd/com.investos.rss.plist.example`, `config/rss_feeds.csv` (phase B only, R21). `src/investos/acquire/base.py` is NOT changed: it already has `AccessMode.REAL_BROWSER`, `BrowserResponse`, `BrowserTransport`, the `browser=` wiring (base R23), the 2.5 s floor (base R28), the daily cap (base R29) and request-header recording (base R30). Python 3.11+ (the Mac runs 3.14.7), stdlib only for everything except the OPTIONAL `playwright` package, imported lazily inside one function (R15). Rule numbers here are this spec's own (R1...), tests A1...; "base R24" means rule R24 of `specs/collect_base.md`, "rss R12" means rule R12 of `specs/collect_rss.md`.

Evidence base: `specs/collect_base.md` (access modes, R17-R33; R23 browser interface), `specs/collect_rss.md` (R1, R3b, R8a, R10, R12, R23, Orchestrator resolutions), `specs/core_manifest.md` (R17 header record rules), `reports/S1-T6/PROBE_2026-11-27.md`, `reports/S1-T6/REPORT.md`, decisions 0002 and 0002a. Facts of 28 Nov (live on Sagar's Mac, M2 Pro, 16 GB, macOS 27.2.1, Python 3.14.7, Google Chrome installed) are the Orchestrator's observations; statements about Playwright or Chrome internals marked (verify) come from the spec writer's knowledge, not from a run here, and the smoke test (R19) exists to confirm them.

## What this spec decides, in one paragraph
One adapter-level class per access mode, because the base forbids a class to change mode by config (base R17): the existing honest `RssFeedCollector` (source `rss`) keeps RBI and SEBI; a new `RssNseFeedCollector` (source `rss_nse`, `access_mode = REAL_BROWSER`) polls the NSE feeds through `RealBrowserTransport`. Routing is a code constant keyed on the URL host (a feed table row cannot choose, rss R1/R23). The transport drives the installed Google Chrome (`channel="chrome"`, persistent profile in the untracked ledger state zone) with Playwright, and issues each request as an in-page `fetch()` from a same-origin page, so the request leaves through Chrome's own network stack with Chrome's own TLS, HTTP/2, headers and cookies. One Chrome per poll cycle, started lazily, closed in a `finally`, with a process reaper so none survives. Headful by default (open question 1). Rate stays on the base limiter, whose real-browser floor is 2.5 s (open question 2).

## Rules (numbered, each gets at least one test and one planted failure)

### The transport
R1. Interface and mode. `RealBrowserTransport.fetch(url)` takes only the URL (base R19: the base sends no headers in `real_browser` mode; there is no header argument) and returns a base `BrowserResponse`. The adapter that uses it has `access_mode = AccessMode.REAL_BROWSER` (the existing enum value `"real_browser"`; nothing new is invented) and is built with `browser=` and no `transport=` (base R23). The transport raises `TransportError` for timeout, page crash, navigation failure, launch failure and an oversize body, and never returns a response it could not read completely. `real_network = True` so a `.invalid` contact is refused as for `UrllibTransport` (base R20).

R2. Chrome's own network stack, nothing else. Every request to a data host is made by Chrome itself: an in-page `fetch()` (R3) issued by `page.evaluate`. The transport and its driver never use Playwright's HTTP client: no `APIRequestContext`, `page.request`, `context.request`, `playwright.request`, `route.fetch`, `route.fulfill`, and no request interception of any kind (`page.route`, `context.route`). A test greps the module for those names (R8) and the fake Playwright of the tests raises if any of them is touched.

R3. The request, one way only: in-page `fetch` from a same-origin page. After the anchor (R4) has put the page on the URL's origin, the driver evaluates one fixed JavaScript function that calls `fetch(url, {cache: "no-store", redirect: "manual", signal: AbortSignal.timeout(<ms>)})` and nothing else: the init object has exactly these three keys (no `headers`, `referrer`, `referrerPolicy`, `mode`, `credentials`, `integrity`, `keepalive`, `method`, `body`), so Chrome chooses every header itself and the cookies are the profile's own (default `credentials: "same-origin"`, which is correct because the page is same-origin). Why this and not navigation: a navigation to an XML URL ends in Chrome's XML viewer, and `response.body()` of a navigation is served by the DevTools protocol, which for text responses returns a body that DevTools has decoded with the response's charset into a string and Playwright then re-encodes as UTF-8 (verify), so a BOM, a non-UTF-8 charset or an invalid sequence need not survive byte for byte; `fetch(...).arrayBuffer()` returns the response entity bytes after transfer and content decoding with no charset step, which is the exact-bytes property the manifest needs (R5). A second reason: no document is rendered, no viewer, no extra sub-requests. `cache: "no-store"` makes Chrome go to the network every time (no heuristic freshness, no conditional request, nothing written to the profile's HTTP cache), which a poller needs and which is an ordinary documented fetch option, not an identity change. `redirect: "manual"` makes a redirect an outcome instead of a second, unrecorded request (rss R4, base R23(a)).

R4. The anchor page. In-page fetch needs a page whose origin equals the data URL's origin. When `session.page_origin()` differs from the origin of the URL being fetched, the transport first navigates the single page to `https://<host>/robots.txt` (constant `ANCHOR_PATH`, the host's own plain well-known file; whatever status it answers, including 403 or 404, the document is same-origin and enough; only the origin of the final page matters). One page, one tab, reused for the whole cycle. The anchor is a real request to the host, so it is governed like one: (a) the transport owns a `HostLimiter` (same state dir, same files as base R27) and calls `acquire(host, interval)` with the effective interval of R14 before the anchor AND again before the data fetch of that same key (only the key that needed an anchor; later keys have just the base's own acquire, so steady state costs no extra wait), so any two requests to a host, anchor or data, from any process, are at least the interval apart; (b) the anchor is not counted by the base's daily counter, so the cap carries a margin for it (R14); (c) if the anchor's status is 401, 403, 429 or 451, the transport does not go on: it returns that anchor as the key's response (`status`, its headers, its body, `final_url` = the anchor URL), so the base's block policy (base R24, host day-block, halt counting) sees it exactly as for any blocked fetch (the base checks blocks before the redirect comparison); (d) if after the anchor the page is not on the wanted origin (a cross-origin redirect), `TransportError("anchor left origin: <final origin>")`; (e) anchor navigation uses `wait_until="commit"` and the call's timeout of R11, with no scrolling, clicking, typing or any synthetic input (decision 0002a).

R5. Byte-exactness and integrity. The stored body is the response entity body exactly as Chrome's `fetch` hands it over, that is after transfer decoding and `Content-Encoding` decoding (Chrome always decodes gzip, deflate and br itself; no browser API exposes the compressed wire bytes, and the honest transport also stores decoded bytes, so manifest hashes mean the same thing in both modes). Chain: in the page, `await response.arrayBuffer()`, check `byteLength <= max_bytes` before encoding, encode the bytes to base64 in 32 KiB chunks (no `String.fromCharCode(...bigArray)`), return `{kind, status, headers, url, redirected, base64, byteLength}`; Python decodes base64 with `validate=True` and requires `len(body) == byteLength`, else `TransportError("body length mismatch")`. Base64 is used so the result does not depend on how Playwright serialises typed arrays (verify). `max_bytes = min(cfg.collect.max_body_bytes, 67108864)`; larger gives `TransportError("body too large")`. Nothing decodes, re-encodes, strips, normalises or "pretty prints" the bytes; a test feeds a body with a UTF-8 BOM, a windows-1252 byte, a NUL and a CRLF and expects identical bytes back.

R6. Status, headers, redirects, errors. (a) Any HTTP status that Chrome delivers (2xx, 3xx via R6(c), 4xx, 5xx) is returned as a `BrowserResponse`; an error status is never raised (the base decides: retry 5xx, block 401/403/429/451, check the rest). (b) `headers` are the page-side `Headers` entries with lowercased names, repeated names joined with `", "`, and with `content-encoding` and `content-length` REMOVED (Chrome already decoded the body, as `UrllibTransport` does, base R21(d); without removal base R22 would reject every compressed feed as "undecoded"). All other headers stay. (c) With `redirect: "manual"` a redirect appears to the page as `type == "opaqueredirect"` with `status == 0` and no readable `Location`. The driver then reads the real status and `Location` from Chrome's own network event for that request (Playwright `response` event, `response.status`, `response.all_headers()`), and the transport returns `BrowserResponse(status=<3xx>, headers={"location": ...}, body=b"", final_url=<Location resolved against the request URL>)`, which makes the base report `redirected to <final_url>` (base R23(a)) and store nothing; if the event was not observed, `status = 0` and `final_url = "redirect:unobserved"` (also `redirected to ...`, nothing stored). The redirect target is never requested. (d) A page-side `AbortError` from the timeout is `TransportError("timeout")`; `TypeError: Failed to fetch` is `TransportError("network error")` (the base retries both: base R4, it cannot tell them apart and need not); a JavaScript exception, a closed page, a crashed renderer or a lost browser connection is `TransportError("browser failure: <short text>")`. (e) The transport itself never retries and never sleeps for retry purposes: retries and backoff are the base's (base R4).

R7. Recording what Chrome sent. After each fetch the transport asks the session for `sent_headers(url)`: the driver listens to Playwright's `request` event for the fetch's URL and reads `request.all_headers()` (the raw header set including `cookie`, `sec-fetch-*`, `sec-ch-ua*`, `user-agent`, `accept-language`, `referer`; names lowercased) (verify). The transport then (a) removes HTTP/2 pseudo-headers (names starting with `:`), which the manifest would reject; (b) validates the mapping against the manifest's header record rules (`specs/core_manifest.md` R17: name tokens, at most 64 headers, at most 16 KiB compact JSON, no `authorization`, `proxy-authorization`, `cookie2`, `set-cookie`, no CR/LF/NUL, str values); on any violation, or if the driver could not observe the request, it returns `request_headers=None` and logs WARNING `request_headers_dropped` with the reason. The data is never lost to a header problem: the base stores the body with `request_headers = None` (allowed for `real_browser`, core_manifest). Cookie values are NOT redacted by the transport: the manifest redacts them (core_manifest R17(c)); the transport never logs a header value (logs name only). The recorded `user-agent` is whatever Chrome sent, which is how a later reader can tell headful `Chrome/...` from `HeadlessChrome/...`. The transport reads or sets no user-agent itself (no `navigator.userAgent` access, R8).

   `chromium_sandbox` and every other launch default stay as Playwright ships them.

R9. Headful or headless. Default is HEADFUL (`headless=False`), the window placed off-screen by `--window-position=-2400,-2400 --window-size=1280,800` (R8(c); "off-screen" is positioning, allowed by Sagar's rule, and Chrome still renders and reports itself as a normal window). Trade-off, stated so Sagar can decide (open question 1): headless Chrome announces itself (`HeadlessChrome/<ver>` in the User-Agent, and Playwright's headless run uses the new headless mode of the same Chrome binary, so TLS is Chrome's) and a site that refuses automation may refuse that UA; being refused is a block (403/429, base R24) and the decision forbids switching identity after a block, so the choice must be made beforehand, not by a fall-back; headful costs a Dock icon and possibly a brief window or focus change every 15 minutes (76 times a day) because macOS may activate a freshly started GUI app (to be observed in the first Mac run; the transport does nothing to steal or to hide focus). `--headless` on the CLI selects headless for a run; there is no automatic switch in either direction. The mode used is logged (INFO `browser_launch`, field `headless`) and appears in the recorded `user-agent`.

### Lifecycle
R10. One Chrome per poll cycle, started lazily. `RealBrowserTransport` launches Chrome (via the driver) on the first `fetch` that needs it and keeps one session, one page, for the rest of the cycle. A cycle that makes no browser request (all NSE feeds not due, the host day-blocked, the table has no enabled NSE row) never starts Chrome. `close()` closes the session (with the R11 timeout, then the reaper) and is idempotent; `poll_cycle`'s caller wraps the transport in `with` or `try/finally`, and a `KeyboardInterrupt` or `SIGTERM` still reaches `close()` (the CLI installs a `SIGTERM` handler that raises `KeyboardInterrupt`; tests call the handler function). After `close()` the transport can be used again only by starting a new launch (the next cycle is a new process anyway). Why per cycle and not a resident Chrome: a 15-minute launchd job is stateless by design (rss R19); a resident Chrome adds a second process lifetime to manage, holds memory on a 16 GB machine for 23 hours a day, accumulates profile state, and survives a crash of the poller unnoticed; the cost of per-cycle is about 1 to 3 seconds of launch, well inside the 600 s budget (open question 3).
   Session death: if a fetch fails with `browser failure` or the watchdog (R11) killed Chrome, the transport marks the session dead and the NEXT fetch launches a fresh Chrome once. If a launch itself fails (`browser unavailable`), a second launch is not attempted in the same cycle: the transport remembers `unavailable` and every later `fetch` raises `TransportError("browser unavailable: <first reason>")` at once, without delay (so 23 feeds do not each pay a launch timeout). Pace of the whole cycle is unchanged.

R11. Hard timeouts and no leftover Chrome. Constants (named, pinned by a test): launch 60 s; anchor navigation `timeout_s` of the call (cfg `collect.timeout_s`, default 30 s); page-side fetch `timeout_s` of the call, via `AbortSignal.timeout`; per-fetch watchdog `timeout_s + 10` s; close 15 s. The watchdog is a daemon thread started per fetch that, if the call has not returned by the deadline, runs the reaper (which kills Chrome, so the blocked Playwright call raises) and flags the session dead; it never touches Playwright objects (the sync API is not thread safe). The reaper `PsReaper.reap(profile_dir, grace_s)` lists processes with `ps -axo pid=,command=` (argument list, no shell), selects those whose command line contains the exact token `--user-data-dir=<absolute profile dir>` (Playwright passes the profile this way; verify), sends `SIGTERM`, waits up to `grace_s` (5 s), sends `SIGKILL` to survivors, and returns the count. It never matches by browser name, so Sagar's own Chrome (another profile) is never touched. The reaper runs: (a) at transport start, before the first launch (clears a Chrome left by a crashed earlier cycle); (b) at `close()`, after the normal close, as a sweep (normally finds nothing); (c) from the watchdog. `ps` failing or the process listing being unparseable is a WARNING `reaper_failed` and never raises. A test with a fake process table proves that only matching command lines are signalled, TERM before KILL, KILL only for survivors.

R12. Profile. Persistent profile directory `<cfg.zones["ledger"]>/.state/chrome-profile/`, created `0700` by the transport if missing; untracked (a test runs `git check-ignore` semantics through the repo's `.gitignore` patterns: `data/ledger/.state/` is already ignored, base R25); never inspected or edited by Investos code (it holds Chrome's cookies and history; nothing from it is logged or committed). One launch per profile at a time: before launching, the transport takes `flock(LOCK_EX | LOCK_NB)` on `<ledger zone>/.state/chrome-profile.lock`, waiting at most 5 s (monotonic, injected sleeper), else `TransportError("browser unavailable: profile busy")`; the lock is released in `close()` and on any exception, and is not inherited by Chrome (`close_fds`). A manual run overlapping a launchd run therefore fails closed on the second one instead of fighting over one profile.

### Routing and the rest of the system
R13. Per-host routing in code. `collector_class_for(feed)` returns `RssNseFeedCollector` when `urlsplit(feed.url).hostname in BROWSER_HOSTS`, else `RssFeedCollector`. Both are in code; the feed table has no access or mode column (rss R3 header unchanged) and a test pins that adding such a column is a `FeedTableError`. `RssNseFeedCollector` subclasses `RssFeedCollector` and changes only `source = "rss_nse"` and `access_mode = AccessMode.REAL_BROWSER`; `keys`, `url`, `check_body`, `unchanged_body`, the date handling and the item rules are inherited (rss R1-R8a). `RssFeedCollector` stays honest, source `rss`, with no `[collect.access.rss]` table (rss R1 and A1 unchanged); RBI and SEBI never reach the browser. The transport refuses any URL whose scheme is not `https` or whose host is not in its `allowed_hosts` with `ValueError` before any browser work (so the transport cannot become a general scraper by a wrong wiring). Both classes are registered with the registry (rss R21); `adapters()` lists both; neither is `date_keyed`. A missing `[collect.access.rss_nse]` table makes `RssNseFeedCollector` raise `ValueError` at instantiation (base R17); the cycle records that feed as a failed slot with the reason text and logs ERROR `access_table_missing` once per cycle (not once per feed), so a forgotten config line is loud and the other feeds are unaffected. `config/investos.example.toml` gains the table as a COMMENTED block (so the "no access tables in the example" rule of base and every existing config test stay true), and the brief tells the Orchestrator to add it to the Mac's `config/investos.toml`.
   If `poll_cycle` gets `browser=None` while an enabled feed routes to the browser, those feeds are recorded as failed slots (`reason = "browser transport not configured"`, no HTTP, no collector built) and WARNING `browser_not_configured` is logged once; honest feeds are unaffected. Source-aware places that today say `"rss"`: the cycle's `apply_outcome` reads the manifest of the collector's own `source`; the freshness/state code is source-neutral; `investos check rss` (rss R20) reads the manifest keys of BOTH `rss` and `rss_nse` and applies "unknown feed id" and "bad key" to both, and a feed whose URL routes to `rss_nse` but has keys under `rss` (or the reverse) is reported as `ghost` (a feed has exactly one source, decided by routing); `extract_items` (rss R14) is a pure function over rows: the loader passes the two sources' rows merged in manifest `fetched_at` order (feed ids are disjoint between sources by the check above), the function itself is unchanged.

R14. Rate, cap, order. The base limiter applies unchanged and is NOT bypassed (base R27, R28): for the `real_browser` adapter the effective interval for `nsearchives.nseindia.com` is `max(configured 1.0, 2.5) = 2.5 s` (base R28; decision 0002a: at most 1 request per 2.5 s per host). So one full cycle of 23 NSE feeds takes about 23 x 2.5 = 58 s plus launch, plus the anchor and its spacing (R4: two extra intervals, 5 s). That is well inside the 600 s budget; the 1.0 s of the example config stays as configured and is simply floored (open question 2). Strictly sequential: one fetch at a time, one tab, no pipelining, no parallel feeds (the cycle is already sequential, rss R10). R16. Host-down rule for the RSS cycle (applies to every host, honest or browser). During one `poll_cycle`, when a feed's run ends `unreadable` with a reason that begins `transport error:` and ends `after 4 attempts` (that is, base R4's retry exhaustion on `TransportError`: a timeout, a connection failure, a refused connection, a browser failure; NOT `http 5xx after 4 attempts`, NOT a 403/429 block which is already a host day-block by base R24), the cycle adds that feed's host (lowercased `urlsplit(url).hostname`) to a cycle-local set `down_hosts`. Every LATER enabled feed in the same cycle whose host is in `down_hosts` is not requested: zero HTTP, no collector built, outcome `not_attempted` with reason `host down: <host>`, recorded exactly as the existing `cycle budget` path (rss R10, R12): a `failed` gap line per feed with that reason, `consecutive_failures + 1`, no `missed` detection change, counted under `failed` in `cycle_end`. The first feed that proved the host down keeps its own reason text (`transport error: ... after 4 attempts`). Feeds on other hosts proceed normally and in table order. The set lives only in the cycle (nothing persisted: the next cycle's first feed on that host probes again, costing at most one feed's 4 attempts, about 124 s of timeouts plus 7 s of backoff, instead of the whole table's). INFO `host_down` is logged once per host per cycle with fields `host`, `probe_feed`, `skipped` (count); `CycleResult.down_hosts` lists the hosts. The base is not changed (the cycle reads the reason from the sidecar as it already does, rss `_sidecar_reason`). A block (403/429) is not host-down. Two successive failures on one host from `http 503 after 4 attempts` are not host-down (the host answers).

R17. Alert coalescing for a dead host. When, within one cycle, two or more enabled feeds of the same host raise a `poll_missed` alarm (rss R13), the cycle sends ONE notification `notify("Invest OS: host down", "<host>: <n> feeds")` (host name and count only, no URL, no header) instead of one per feed, still marks every feed's `alerted["poll_missed"]` for the IST day (so no later cycle repeats it), still logs ERROR `feed_alarm` per feed, and still sends the single-feed message of rss R13 when only one feed of a host alarms. `content_stale` alarms are not coalesced. ## Edge cases
- Chrome is installed but cannot start in a LaunchAgent (no GUI session, e.g. a launchd job run over SSH, or the user is logged out): `launch` raises `TransportError("browser unavailable: ...")`, the feed fails with `transport error: browser unavailable ... after 4 attempts`, the rest of the NSE feeds become `not_attempted` through R16, and the next cycle tries again. Honest feeds (RBI, SEBI) are polled before or after as the table order says; they are unaffected.
- Browser starts but the anchor is answered with a block page: R4(c); host day-blocked for the IST day for every adapter on that host (base R24); the NSE feeds of this cycle are `not_attempted` with the base's reason; Chrome is closed at cycle end.
- Anchor returns 404 or an empty body: fine, the page is same-origin; the data fetch proceeds.
- A feed URL redirected by the server (`.com` to `.in`): `redirect: "manual"` makes it `redirected to <target>`, nothing stored, rss R4 (fix the table, never follow).
- The body is not a feed (Chrome's own error page text cannot occur: fetch never renders one); a 200 HTML challenge page is `unreadable` by `check_body` (rss R5) and, if a challenge signature is configured later, a block (base R24).
- Chrome shows a first-run dialog or a profile-lock error in a headful window: the fetch cannot proceed, the fetch times out, `TransportError`; the watchdog and reaper clean up; nothing clicks on a dialog (decision 0002a: no synthetic input). The Orchestrator's first manual launch of the profile should be done once by hand to clear first-run prompts, noted in the brief.
- Chrome updates itself between cycles: nothing to do; the recorded UA shows the version.
- The Mac sleeps in the middle of a cycle: the page-side timers and the watchdog may fire on wake; the result is a timeout `TransportError`, retried by the base, and the host-down rule may then mark NSE down for the rest of that cycle; the next slot recovers; the gap ledger holds the failed slots.
- Two feeds fetched back to back with identical bytes: unchanged-body dedup (rss R8a) as usual; the anchor is not repeated within the cycle (the page stays on the origin).
- `final_url` for a normal fetch is the URL Chrome reports for the response; a fragment-only difference is ignored by base R23(a).
- The profile grows: `cache: "no-store"` keeps the HTTP cache out; cookies and local state are small. Pruning is a human task and not in this spec.
- Clock moves or `monotonic` jumps: the watchdog uses the injected monotonic clock; tests drive it with a fake and a fake thread-less timer.
- A run of the poller on Linux CI or any machine without Chrome: only the fake driver is used; the real driver is never constructed in tests except with the fake `sync_playwright` object.
