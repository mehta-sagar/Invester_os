## What this spec decides, in one paragraph
Seven-to-eight endpoints, each a row of a code-shipped table (`config/backfill_endpoints.csv`, R2) that starts `to_probe`. A PROBE command (R3-R5), run by a script on the Mac with no chat tokens, measures shape, row cap, earliest date and time-of-day presence for every endpoint and writes a human report and a machine plan input; an endpoint whose probe is not `confirmed` (bound to the table row's hash) cannot be backfilled. A PLANNER (R6-R8) cuts `[start, end]` into disjoint date windows below the cap; a window that returns exactly the cap (or whose halves sum to more than the whole) is never trusted, it is split and refetched. Every window outcome is one line in an append-only LEDGER (R9), so a run stops at any moment (sleep, block, Ctrl-C) and resumes without refetching; the manifest still makes a refetch idempotent (R10). Bytes are stored raw and untouched through the manifest, source `backfill_<endpoint>`, `access_mode = real_browser` (R11). Pacing, one Chrome, the nightly window and budget, the block stop and the no-stealth rules are R12-R16. The runner is a thin loop over the unchanged base `Collector` (R17), scheduled nightly by launchd (R18), observed by `investos backfill status` and `investos check backfill` (R19-R20).

## Rules (numbered, each gets at least one test and one planted failure)

### The table and the probe
R1. Collector does not parse. The collector (R17) stores the response bytes exactly as the transport returns them (browser R5) and keeps no derived copy. `check_body` may inspect the bytes ONLY to (a) confirm the body is JSON of the probed shape, (b) count rows at `rows_path`, (c) read the `date_field` of each row for the in-file date check. It never modifies, normalises, deduplicates or filters rows; parsing into tables is a later stage. The probe (R4) is a measuring tool: it may parse JSON, and nothing it computes is stored as data.

R2. The endpoint table. `load_endpoints` reads `config/backfill_endpoints.csv` strictly: the exact header, unique `endpoint_id` matching `^[a-z][a-z0-9_]{0,30}$`, `page_url`/`anchor_url`/`api_path` start with `/` (paths on the page's own origin) or are `https://www.nseindia.com/...` (anchor only); `params` holds only the placeholders `{from}`, `{to}`, `{symbol}`; `date_format` is one of `DD-MM-YYYY`, `YYYY-MM-DD`; `max_window_days` >= 1; `row_cap` empty or a positive integer; `start_date` an ISO date not before 2000-01-01 and not after the run date; `status` in the five values; `to_inclusive` in `yes`, `no`, empty. Any violation, unknown column, duplicate id or a host other than the two NSE `www` hosts is `EndpointTableError`. `api_path` never contains a scheme or host (the API origin is the anchor page's final origin, R14). A test pins that the shipped table has the eight rows of the catalogue, all `to_probe`, and that every `known_at_rule` cell is non-empty.

R3. Probe first, refusal otherwise. `run_backfill` calls `load_probe(cfg, ep)` for each endpoint; an endpoint whose probe is absent, `needs_review`, older than 30 days, or whose stored `row_hash` differs from the current table row's `row_hash()` is NOT backfilled: it is reported as `refused: probe not confirmed` (status output, one INFO line), zero requests are made for it, and the run goes on with the other endpoints. If no endpoint is confirmed the run exits 0 with nothing done and says so. There is no flag that skips the probe.

R4. Probe procedure (stage 0), `investos backfill probe`, a script with no chat involvement. For each selected endpoint, sequentially, through the same transport, limiter, block rules and budget as the backfill (R12-R16; probe requests count against the night budget; the probe obeys the nightly window unless `--outside-window`), the probe makes the following requests (about 40 per endpoint, 320 in all, about 13 minutes), stores every body in the manifest (source `backfill_probe`) and records:
   (a) Anchor: navigates `anchor_url`, records the HTTP status of the anchor, the page's FINAL origin (the `.com` to `.in` redirect is recorded as `api_origin`), and whether the origin matches the previous probe; the run's origin alias is built from this (R14).
   (b) Shape: for a recent 1-day window (the last completed weekday, at least 3 days old) fetch and record: HTTP status, content type, whether the body is JSON, the top-level type (list, or object with the key that holds the rows = `rows_path`), the sorted field names of the first row, the candidate date fields (names whose values match a date or datetime pattern), response size. A body that is not JSON, or an HTML page, is a probe failure for that endpoint (`needs_review`), never a shape.
   (c) Window ladder and cap: on a busy reference month (the first full month of the most recent complete quarter) fetch windows of 1, 3, 7, 14, 31 days (all starting at the same date) and record the row count of each; then derive `row_cap` by these rules: the cap is `n` when (i) the same count `n` is returned for two windows of different widths, or (ii) the count equals one of the round numbers {10, 20, 25, 50, 70, 100, 200, 250, 500, 1000, 2000, 2500, 5000, 10000} and the counts of its two halves (fetched separately) sum to more than `n`. Otherwise `row_cap = none observed` and `max_safe_rows` = the largest count seen. Counts that DEcrease as the window widens (a wider window with fewer rows than a narrower window inside it) mark the endpoint `undercount` (the results listing fact): the probe records it, sets `max_window_days` to the largest width whose count equals the sum of its halves in three trials, and fails the endpoint (`needs_review`) if no width of one day satisfies that.
   (d) Inclusivity: fetch day D, then D-1..D and D..D+1, to decide `to_inclusive` and whether `from` is inclusive: the rows of D must appear exactly once across the two-day windows split at D. Recorded as `to_inclusive` yes/no; an ambiguous result is `needs_review`.
   (e) Earliest date with data: starting from the table's `start_date`, fetch a 7-day window at the start of each year going FORWARD until a window has rows (`first_year`), then bisect inside that year to the month and the week (about 12 requests). Also fetch one window one month BEFORE the found date to confirm it is empty. Records `earliest_date`. If the table's `start_date` already has data and a window before it also has data, the probe walks backwards in 1-year steps (at most 25 requests) until empty, and records the earliest found.
   (f) Time of day: on one sampled window per five-year band from `earliest_date` to the present, record whether the `date_field` values carry a time (pattern match on the value text, no parsing into dates), as `all`, `none` or `mixed`, and the first band where `all` begins; then bisect (at most 8 requests) for the first year with time. Output `time_of_day` = `none_before:<date>` or `all`/`none`/`mixed`. Rows without a time are what the `known_at` rule turns into end-of-day (table column).
   (g) Shareholding only: determine whether the per-quarter listing (date params) returns a market-wide list; if not, the per-company form is probed with three symbols (one large, one small, one delisted if known) for depth (oldest quarter returned) and size; records `mode = per_company | per_quarter`, `symbol_source` (the symbol list the Orchestrator supplies, R22), depth.
   (h) Determinism: re-fetch the reference 7-day window once, 2.5 s after the first time it was fetched; the row counts and, when the body bytes differ, the sets of row texts must be equal, else `needs_review` (`non-deterministic`), and the body hash difference is noted (a timestamp field in a wrapper is acceptable, rows differing are not).
   (i) The probe never makes more than 60 requests for one endpoint; on exceeding it stops that endpoint as `needs_review`. A block stops the whole probe (R15).

R5. Probe outputs and confirmation. The probe writes `reports/backfill/PROBE_<IST date>.md` (per endpoint: the measurements above in a table, the derived values, the decision, the request count, the raw manifest keys) and `<ledger zone>/backfill/probe.json` (canonical JSON, schema 1): per endpoint `{endpoint_id, row_hash, probed_at, api_origin, rows_path, date_field, date_format, to_inclusive, row_cap | null, max_safe_rows, max_window_days, earliest_date, time_of_day, undercount, mode, status, reasons[]}`. `status = "confirmed"` iff every one of (a) to (h) produced a value without a failure flag; otherwise `needs_review` with reasons. The probe NEVER edits `config/backfill_endpoints.csv`; adopting a probe value that differs from the table (for example `start_date`) is done by changing the row (a human or the Orchestrator), which changes `row_hash()` and sends the endpoint back through the probe. A probe result with `row_cap = none observed` is confirmed but forces R8's audit to run on every `audit_every`-th window as usual. `load_probe` returns the stored result only when its `row_hash` equals the table row's; a probe re-run replaces the endpoint's entry (the previous entry is kept in the report only).

### Planning and completeness
R6. Window planner. `plan_windows(ep, probe, end)` returns the ordered, DISJOINT, gap-free list of inclusive date windows covering `[max(ep.start_date, probe.earliest_date), end]`, where `end` is the last completed IST day (today minus 1; not today: partial days would be sealed as complete). Each window is at most `probe.max_window_days` days and is sized so that `expected_rows <= 0.8 * cap` where `expected_rows` = the busiest-month density from the probe's ladder scaled to the window width (so the common case needs no split); when `row_cap` is none, windows are `max_window_days`. For endpoints with a trading-day nature (`bulk_deals`) the windows are cut on trading days only (days confirmed non-trading by `config/calendar` are skipped; unknown days are kept). The windows tile the range exactly: `end_i + 1 day == start_{i+1}`. The plan is written to `plan/<endpoint>.json` with the planner inputs and re-derived (deterministically, same file) whenever the probe or `end` changes; windows already `fetched`/`empty` in the ledger keep their ledger state even if a re-plan would draw different borders (a re-plan only adds windows for the uncovered range; borders of done windows are never moved). For `shareholding` in `per_company` mode the plan is one window per symbol (`part = <symbol>`, start/end = the endpoint range).

R7. Adaptive split. `split(key)` halves an inclusive window by calendar days (the first half gets the extra day when odd) into two keys with `part` suffix `a` and `b` appended (`""` to `a`/`b`, `a` to `aa`/`ab`); the halves tile the parent. After a batch, every window whose outcome is `incomplete` (base R10: the row count equals or exceeds `page_limit`) gets a `split` ledger line (nothing was stored for it, base R10) and its two halves are queued as new windows in the next batch of the same night; splitting stops at a one-day window (R24). A window is never trusted when its row count equals the known cap, equals a round-number cap detected by the probe, or exceeds the cap. A `split` window has no manifest row. Splitting is never skipped to save requests.

R8. Completeness checks. (a) Per window, in `check_body`: the body is JSON of the probed shape (else `unreadable`, never stored); the row count `n` is taken at `rows_path`; `n == 0` is `FETCHED_EMPTY` (stored; some windows are legitimately empty); every row's `date_field` (when the probe found one) must fall inside the window (base in-file date check; a row outside gives `rejected`, never stored, window `failed` with reason `date outside window`); `page_limit` is the probed `row_cap` (base R10: `n >= cap` means `incomplete`). (b) Audit: every `audit_every`-th window that ended `fetched` (counted per endpoint, deterministic: window index modulo `audit_every`, so tests are exact) and every window with `n >= 0.5 * max_safe_rows` when the cap is none observed, is re-fetched as its two halves (stored under the `a`/`b` keys) right after the batch; if `n_a + n_b > n` the parent is `superseded` (the halves become the plan of record, their `fetched` lines stay, and `max_window_days` for the endpoint is halved for all windows not yet fetched, written as an `audit_shrink` line in the ledger and honoured by the planner), if `n_a + n_b < n` the endpoint is `needs_review` (inconsistent counts: rows disappear when the window narrows) and the runner stops it; if equal the halves are kept as audit evidence (stored) and the parent stays. (c) End of endpoint: when every window is `fetched`/`empty`/`superseded` (with its children done) and the tiling check of `check backfill` (R20) passes, the endpoint is `complete`; any `unsplittable`, `failed` or `blocked` window keeps it `incomplete` and listed.

### Ledger, resume, storage
R9. The window ledger is append-only JSONL with the writer and reader rules of base R25: exclusive `flock` on `<file>.lock`, one `write`, flush, fsync, directory fsync at creation, refusal to append to a file whose last byte is not a newline; the reader parses strictly under a shared lock when the tail is unterminated (a torn tail that persists raises `LedgerError`), rejects unknown fields, unknown events, `schema != 1`, a `date` that is not the IST date of `ts`, a window with `start > end`, a `fetched` line without `sha256`/`rows`/`logical_key`, a `part` that is not `[a-z]*`, and a `fetched`/`empty` window whose key is not in the manifest (checked by `check backfill`, R20; the runtime reader only needs the file). Fail closed: `LedgerError` at start or mid-run means zero further requests, status `error`, ERROR log. A window's state is its last line; `superseded` and `split` windows are not pending. Events are written AFTER the corresponding manifest write (so a crash between them leaves a stored window with no ledger line: it is `skipped` by the base on the next run and its ledger line is repaired by R10(c), never refetched).

R10. Resume and idempotency. (a) Pending windows = plan windows (and queued children) whose state is not `fetched`, `empty`, `superseded` or `split-with-children-done`; order: by endpoint in table order, OLDEST window first within an endpoint, so a partial history is a contiguous prefix and `earliest_date` of usable data is meaningful. (b) A run killed at any point (power, sleep, SIGTERM, Ctrl-C, block, budget) loses at most the window in flight, which is simply pending next time; no window is ever recorded `fetched` without its manifest row. (c) Idempotency through the manifest and the base: a pending window whose `logical_key` is already in the manifest is `skipped` by the base R9 (zero HTTP) and the runner appends the missing `fetched` ledger line from the manifest entry (`sha256`, and `rows` by counting the stored bytes through the same `check_body` count, no network). A second run over a completed plan makes zero HTTP calls, zero Chrome launches (Chrome is started lazily, browser R10) and appends no ledger line. (d) The same window with the same bytes never makes two manifest rows (manifest idempotence by sha); the same window with DIFFERENT bytes (the source changed between fetches) is a manifest conflict of the existing manifest rules and surfaces as `failed` with the manifest's reason; it is never overwritten.

R11. Storage. Each `fetched`/`empty` window: `ManifestStore.store(source = "backfill_<endpoint_id>", body, url=<api url>, source_version="backfill-v1", logical_key="<endpoint_id>/<start>_<end>[/<part>]", ...)` with the transport's recorded headers; nothing is decoded, re-encoded, merged with another window or deduplicated. The URL is built from `api_origin` of the probe + `api_path` with `{from}`/`{to}` formatted per `date_format` (and `to` adjusted by one day when `to_inclusive` is `no`: the window's last day is requested as `to = end + 1`), and the probe's origin check (R14) runs first.

### Pacing, safety, schedule
R12. Pace. All requests, anchor and data and probe, are sequential, one tab, one Chrome per run, through the base limiter and the transport's `HostLimiter` with the real-browser floor `max(configured, 2.5)` seconds per host (base R28, 0002a): the pacing host is the API origin host (`www.nseindia.in`), and the anchor on `www.nseindia.com` is limited under its own host name too, spaced from the previous request regardless of host (the runner keeps a run-level monotonic last-request time and waits for 2.5 s since ANY NSE `www` request of this run). No concurrency, no pipelining, no second Chrome of the backfill, no parallel endpoints. No jitter or randomisation of timings (decision 0002a; browser R8).

R13. Nightly window and budget. (a) The runner computes the IST window from `[backfill] window_start`/`window_end` (default 00:30 to 06:30) from the injected clock. Outside it the runner exits 0 with status `window_closed` and starts no Chrome, unless `--outside-window` is given; even with that flag it refuses (exit 1) between 08:30 and 16:30 IST on Monday to Friday, so a market-hours day never carries a backfill (the RSS poller keeps priority; there is no override). (b) The night budget is `nightly_budget` (default 8000) requests per window, counted by a run-level counter that increments for EVERY transport request: data fetches, retries, anchors (one per endpoint switch via `set_anchor`, one per Chrome restart), probe requests and audit halves. The counter is persisted in `night.<date>.count` (so a second run in the same night continues the count, as base R29) and the run stops cleanly with status `budget` when the next request would exceed it. The base's `daily_cap` of each source (default 9000) is a second, independent safety net. 8000 requests at 2.5 s are 5.6 h, which fits the 6 h window with room for launch, retries (up to 3 sleeps of 1, 2, 4 s) and the 25-window batch overshoot. (c) Window and budget are checked BEFORE each batch of `batch_windows` windows (default 25: at most about 25 x (1 + a few retries) requests, at most about 4 minutes of overshoot) and a batch is shortened so that its worst case without retries fits the remaining budget; the clock is the injected one (no system clock in tests).

R14. Browser use and the redirect. (a) One `RealBrowserTransport` per run with `profile_name = "chrome-profile-backfill"` (a profile and lock separate from the RSS poller's, so a six-hour backfill never makes the 15-minute poll fail with `profile busy`), `allowed_hosts = {www.nseindia.com, www.nseindia.in}`, `origin_aliases = {"https://www.nseindia.com": "https://www.nseindia.in"}` (built from the probe's recorded `api_origin`, not hard-coded), `anchor_for` = the endpoint's `anchor_url` (resolved on the `.com` host, which redirects to the `.in` host). (b) The anchor must be the REAL page (R2: `anchor_url`), never `robots.txt`; at each endpoint switch the runner calls `set_anchor(anchor_url)` (C3). After the anchor the runner compares the page's final origin with the probe's `api_origin`; a mismatch (the site moved again) stops the run with status `error` and reason `origin changed: <old> -> <new>`, a Sagar item; the runner never rewrites the origin by itself. (c) Data requests are in-page `fetch()` from that page through the existing transport only (browser R2, R3): no navigation to API URLs, no `page.request`, no headers set by us, no cookies read or written by us, no interception. The recorded request headers are Chrome's. (d) A non-200 anchor is logged (WARNING `anchor_status`) and the fetch proceeds, as browser review D1; a 401/403/429/451 anchor is a block (R15). (e) A body that is HTML (a challenge page, an interstitial) is `unreadable` by R8(a) and, when it matches a `challenge_signatures` entry captured later, a block; with no signature configured, three consecutive HTML bodies for three different windows of one endpoint stop that endpoint for the night (status `stopped`, reason `non-JSON responses`) and are reported (Sagar item), without any retry on another identity. (f) The Chrome process is closed in a `finally` and reaped (browser R11); `SIGTERM` and `KeyboardInterrupt` reach `close()` (browser R10).

R15. Stop on a block. Any response with status 401, 403, 429 or 451 (anchor or data), or a challenge signature, is a block under base R24-R26: the base marks the window `unreadable`, writes the host `blocked` event for that host, aborts its run. The runner additionally (a) treats a block on EITHER NSE `www` host as a block of both (it appends the same `blocked` event for the other host through `access` state helpers, so the `.com` anchor host and the `.in` API host stop together), (b) appends a `blocked` ledger line for the window in flight, (c) stops the whole runner (all endpoints) with status `blocked`, exit 3, (d) calls `notifier.notify("Invest OS: NSE backfill blocked", "<host> <status>; backfill stopped for the IST day")` once, (e) never retries, never changes anything about the browser, profile or timing, never tries another host or the `nsearchives` host, and (f) at its next start (the next night) first reads the host block state; a host blocked for the IST day, or a halted source (base R26, 3 blocked days in 7), means zero Chrome launches and zero requests, exit 3 with the printed reason, until `investos access clear <source> --decision <id>` (base R26) is done by Sagar. A `halted` source stops only its own endpoint, a host block stops everything.

R16. No evasion, enforced by tests. The `src/investos/backfill/` modules and the amended parts of `browser.py` contain none of the forbidden strings of browser R8(a) (grep over the source text, comments and docstrings included): no stealth or webdriver manipulation, no user-agent or header setting, no init scripts, no CDP sessions, no proxy or IP rotation, no CAPTCHA solving, no paid scraping actors, no random or jitter, no synthetic mouse, keyboard or click, no `random` import. The only page code is the transport's fixed `fetch` and the anchor navigation. The launch keywords stay exactly those of browser R8(b). A recording fake of Playwright proves this for the runner end to end (the fake raises on any other API).

R17. Integration with the base (no change to `base.py`). `make_collector_class(ep, probe)` builds, per endpoint, a `Collector` subclass with `source = "backfill_<endpoint_id>"`, `source_version = "backfill-v1"`, `access_mode = AccessMode.REAL_BROWSER`, `page_limit = probe.row_cap` (None when none observed), `archive = False`, `date_keyed = False`. The collector is built with `browser=<the one transport>` and no `transport=` (base R23). `keys(run_range)` yields the logical keys of the batch given by the runner (the runner passes the batch through the instance, one key per window; the `RunRange` is `[first window start, last window end]` of the batch, and the base's `end >= start` rule holds because windows are sorted oldest first); `url(key)` builds the API URL (R11); `check_body` implements R8(a). The runner calls `run()` per batch, reads the `RunResult.outcomes` and appends ledger lines (`fetched`, `empty`, `split` for `incomplete`, `failed` for `unreadable`/`rejected` with the base's reason, `blocked`), then queues children (R7). Because the base aborts a run when a key becomes unreadable through retry exhaustion (base R8), a `failed` window ends the batch; the runner starts the next batch (the failed window is retried only on a later night, never in the same night, and after 5 `failed` lines in total it is marked `needs_review` in status and skipped until Sagar looks).

R18. Scheduling. `ops/launchd/com.investos.backfill.plist.example`: label `com.investos.backfill`, `ProgramArguments` = `caffeinate -i <venv>/bin/investos backfill run` (so the Mac does not idle-sleep while running; `caffeinate` is a macOS system tool, not an evasion), `StartCalendarInterval` `Hour 0 Minute 35`, `RunAtLoad true`, `LimitLoadToSessionType = Aqua` (headful Chrome needs the logged-in session), stdout and stderr under `data/ledger/.state/`. A comment documents: launchd uses the Mac's local zone (the Mac must be set to Asia/Kolkata); a job missed because the Mac slept runs when it wakes (the runner then checks the window and exits 0 if it has passed); an optional `sudo pmset repeat wakeorpoweron MTWRFSU 00:25:00` wakes the Mac for the window (open question 5); installing the job is a human step after the probe is confirmed and a first supervised night. The runner exits 0 with `complete` when every confirmed endpoint's plan is complete, and the job does nothing afterwards (the plist is removed by hand when the report says so).

R19. `investos backfill status`. One line per endpoint, in table order: `endpoint, probe status (confirmed/needs_review/to_probe/stale), windows done/total (total = plan windows plus split children not yet counted), rows (sum of ledger rows of live windows), splits, unsplittable, failed, last error (reason and ts of the last failed/blocked line), ETA`. ETA = `remaining windows x avg requests per window x 2.5 s`, where avg requests per window is measured from the ledger and the night counters (default 1.1 until measured), converted into nights at `nightly_budget`; printed as `N nights (~H h)`; `unknown` when nothing was measured; `blocked until <IST date>` when a host block is active. A footer line gives the sum, today's night counter and the next window opening. It makes no network call, starts no browser and reads ledger, probe, plan and counters only.

R20. `investos check backfill` (read-only, the `investos check` harness, base case for the planted-failure harness). It reports and fails on: (a) a ledger line referencing an endpoint or window not in the plan or its descendants (`ghost_window`); (b) a `fetched`/`empty` window with no manifest entry for its `logical_key`, or a manifest key of a `backfill_*` source with no ledger line (`unrecorded_fetch`, repairable by R10(c)); (c) TILING: the live windows of an endpoint (those not `split`/`superseded`) must be disjoint and, where the endpoint is declared complete, gap-free over the plan range (`overlap`, `gap`); (d) a sample of 1 percent of done windows (at least 5): the stored bytes verify against the manifest sha (manifest read-verify) and the row count recounted equals the ledger `rows` (`rows_mismatch`); (e) a done window whose rows are at or above the cap (`cap_window_trusted`); (f) an endpoint backfilled without a `confirmed` probe whose `row_hash` equals the table row (`unprobed_fetch`) or with a probe older than 30 days while windows are still pending (`stale_probe`, warning); (g) a `blocked` line within the last 7 days (warning, with the host state); (h) the night counter above the budget (`budget_exceeded`); (i) the forbidden-string grep of R16 (`stealth_string`). Exit 0 when only warnings.

R21. Notifications (injectable `Notifier`, default `NullNotifier`; no test runs a command). One per event, never per window: the block of R15; a night summary at the end of every run that did work (`"Invest OS: backfill night: <requests> requests, <windows> windows, <rows> rows, <n> splits, <k> failed"`); `complete` once (`"Invest OS: NSE backfill complete"`); an endpoint turned `needs_review` by an audit or R14(e). Titles and messages carry counts and endpoint ids, never URLs, headers or cookie values.

R22. Inputs the Orchestrator supplies before the probe, not code: (a) the exact API paths and param names from the page network log (copy into the table), (b) for `shareholding` in `per_company` mode, a symbol list file `config/symbols_backfill.csv` (one symbol per line; source: the NSE securities master the project already holds or a manual download), validated like the table (strict header `symbol`, `^[A-Z0-9&-]{1,20}$`, no duplicates), (c) the nine `[collect.access.backfill_*]` tables (eight endpoints plus `backfill_probe`) and the `[backfill]` block added to the Mac's `config/investos.toml` (the example file carries them commented).

R23. Sleep, gaps and clocks. A Mac that sleeps mid-run stalls the process; on wake the monotonic clock may jump. The limiter and counters already use wall time with the clamps of base R27; additionally the runner re-reads the injected wall clock after every request and, when the gap since the previous request exceeds 120 s, logs WARNING `resume_after_sleep`, re-checks the window and the budget, and re-anchors (`set_anchor`) before the next data fetch (a page that stayed open across a long sleep may have lost its session cookies). No window is ever marked done on a response that arrived after a gap and fails its checks. A night with no run at all is simply a night not used; there is no catch-up burst (the daily budget is not carried over).

R24. One-day window at the cap (`unsplittable`). A one-day window whose count is at or above the cap cannot be halved by date. The window is recorded `unsplittable` (nothing stored: base R10), counted in status, listed in the report, and the runner never retries it and never alters the request to squeeze more rows (no extra params that were not probed). Whether such days are filled another way (per-symbol queries, manual CSV download, licensed feed) is Sagar's decision after the first pass (open question 4).

R25. `known_at` is not computed here. The table column is the contract for the later parse stage: this task stores raw bytes and the probe's `time_of_day` finding only. A raw window's `fetched_at` (the manifest's own, in 2026) is the time the raw was seen, never a point-in-time stamp for a 2005 row. Edge: history is "as the endpoint serves it today" (restatements, corrections, delisted names may be missing); the report says so.

## Edge cases
1. A window returns the cap exactly (70 for bulk deals): `incomplete`, nothing stored, split; a one-day window at the cap is `unsplittable` (R24).
2. A window returns fewer rows than the sum of its halves (silent truncation, the results listing fact): the audit (R8(b)) shrinks the plan; the probe catches it first (R4(c) `undercount`).
3. A holiday or a weekend: an empty list is `empty` and stored (legitimate); an empty body or `{}` or an HTML page is `unreadable`, not empty.
4. A window straddling the date where times start appearing (about 2012): no effect on fetching; the probe records the switch date; rows are stored as served.
5. `to_date` treated as exclusive by an endpoint: the probe's inclusivity test (R4(d)) sets `to_inclusive = no` and R11 requests `end + 1`; a wrong guess would show up as rows outside the window (`rejected` by R8(a)) or a tiling gap in the audit.
6. The `.com` page redirects to `.in` once at the start of every anchor; if the redirect goes anywhere else, or stops redirecting, R14(b) stops the run with the origin message instead of fetching on an unexpected origin.
7. The Mac sleeps at 02:10 and wakes at 07:00: the in-flight window is pending next night; the missed night's budget is not carried over (R23).
8. launchd fires at 00:35 while a manual run is still going: the Chrome profile lock (browser R12) and the night counter make the second process exit with `profile busy` and no request.
9. Two windows return the same row (a filing broadcast across midnight appears in two adjacent windows because of an inclusive-date mismatch): not deduplicated here (R1); the audit and the tiling check make overlaps visible; the parse stage dedups by natural key.
10. Probe `confirmed` yesterday, table row edited today (for example the `start_date` is moved): `row_hash` differs, the endpoint is refused until re-probed (R3, R5).
11. The ledger and the manifest disagree after a crash: manifest wins (R10(c)); the ledger line is repaired, never the manifest edited.
12. An endpoint returns 200 with a JSON error object (`{"status":"error"}`) for one window: `check_body` rejects it (shape), no store, `failed`, the endpoint continues; five such lines for the same window mean `needs_review`.
13. The run date changes while a run is in flight (past midnight IST): the night counter keys on the IST date of the WINDOW START so 23:50 to 02:00 runs share one counter; the plan end (last completed day) is fixed at run start.
14. A symbol delisted long ago for `per_company` shareholding returns an empty or an error: empty is `empty`; an error shape is `failed` with the reason; neither stops the endpoint.

## Not in this module
Parsing, normalising, deduplicating or typing any backfilled row (a later stage, driven by the `known_at_rule` column); computing `known_at`; XBRL, PDF and attachment downloads linked from announcements or shareholding rows (a separate task, with its own spec, hosts and caps); the BSE history; any `nsearchives` host fetch (the RSS poller's); gap-fill after a missed RSS poll (a later small use of the same planner); CAPTCHA, proxies, stealth or any identity change (forbidden, 0002a); changing `base.py`, `access.py` or `manifest.py`; running the probe or the backfill from CI; installing launchd jobs (a human step); concurrent endpoints or a second Chrome.

(a) 8,000 requests in the 00:30 to 06:30 IST window (recommended: about 3 nights for everything in the estimate, 5.6 h of Chrome a night, nothing near market hours); (b) 4,000 a night for about 5 to 6 nights (gentler, longer).
