# Brief S1-T5: In-file date check in the collector base + DuckDB resource caps
- Stage: 1        - Branch: task/S1-T5        - Algorithm section: §4 "What every collector does" (body check, date check); 16 GB Mac resource limits
- Agents: Spec writer (Sonnet) → Test writer (Sonnet) → Builder (Sonnet) → Reviewer (Sonnet, fresh)

## Goal
Two small changes, both from S1-SPEC2. (1) `specs/collect_base.md`, "Stage 1 amendment 2" (R34 to R41, A59 to A71): HTTP 200 is never proof of a trading day. A date-keyed collector declares how the trade date is read inside the file (`internal_dates`, or a written waiver); the base compares it with the requested key and turns a mismatch or a missing date into the new outcome `rejected` (reason `date_mismatch` or `date_missing`), storing nothing, with the sidecar counting `rejected` and recording `date_check`. Planted case: a Sunday URL that returns Friday's byte-identical file. (2) `specs/core_config_log_db.md`, "Stage 1 amendment" (R20 to R25, A31 to A41): an optional `[duckdb]` config section (`memory_limit` default `5GB`, `threads` default 4, `temp_directory` inside the data root) applied by `open_db` on every connection together with `preserve_insertion_order = false`, so a heavy query on the 16 GB Mac spills to disk instead of swapping.
